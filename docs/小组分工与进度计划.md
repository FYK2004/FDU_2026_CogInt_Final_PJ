## 1. 分工原则

1. **按交付物分工，不按报告章节分工**——章节是结果，交付物才是可验收的东西。
2. **写权限互斥**——每人只改自己名下的文件；跨文件改动先打招呼，避免 Git 冲突。
3. **每条主线一个 DRI（直接责任人）**——出问题找得到人，不搞「大家一起负责」。
4. **上下游用文件交接**——A 产出 `data/processed`，B 消费它产出 `forecast.json`，
   C 消费两者产出报告，D 消费报告产出展示。接口就是文件，不靠口头同步。

## 5. Git 协作规范

```powershell
# 每次开工前
git pull --rebase origin main

# 建自己的分支（用角色前缀）
git checkout -b feat/data-refresh-a
# 或 fix/report-pagenum-c

# 提交（小步、单一目的）
git add <自己的文件>
git commit -m "data: 补采 10/14 判决点并新增数据自检"

# 推送并开 PR
git push -u origin feat/data-refresh-a
```

- 分支命名：`feat/`、`fix/`、`docs/` + 简短英文 + 角色字母。
- **不直接 push main**；PR 至少 1 人 review（重点看数字有没有被改动）。
- 冲突高发文件：`README.md`、`forecast.json`、`docs/项目报告.md`——只由 owner 改。
- 大文件（`data/raw/articles/*.htm`）非必要不重复提交。

## 6. 例会机制

- **每周一次 30 分钟站会**：每人 3 句话（上周交付 / 本周计划 / 卡点）。
- **判决点当天加开 15 分钟**：只看「数据变了没、概率变了没、报告要不要改」。
- **单一信息源**：所有数字以 `data/processed/forecast.json` 为准，
  群里转述必须带 commit hash。
